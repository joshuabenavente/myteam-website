## 1. Executive assessment

The site is discoverable in public search results: the homepage, team schedules, and roster pages appear with substantial sports data. The biggest technical gap is in the delivery path for player and game detail URLs. The Vite build writes static HTML files for the picker, each team, and each roster, but it writes only a generic `404.html` for deeper routes. Those detail pages depend on client-side React and JSON requests; their direct HTTP status on the custom domain has **not** been measured. The base HTML has a generic description and no canonical or structured data. The source tree has no robots or sitemap file or generator. These are source-code findings, not claims about what a crawler currently indexed.

Some public search excerpts display the site's own “Couldn't reach myteam.fans” message in place of data. That message is produced by [`src/lib/data.ts`](https://github.com/joshuabenavente/nuggets-tracker/blob/main/src/lib/data.ts) when required JSON fetches fail. Whether it remains in Google or Bing's indexed copy, and why the fetch failed, require URL Inspection and server logs. Fixing the detail-route response and dependable crawl content outranks adding keywords or schema.

**Product constraint:** preserve the fast, simple, ad-free tracker. No articles, betting pages, automatic thin-page generation, or extra UI purely for SEO. “No ads. No bets. Just the facts.” and “All game. No noise.” are brand copy, not substitutes for descriptive page titles.

## 5. Indexing and canonicalization strategy

| Template | Intended treatment | Conditions |
| --- | --- | --- |
| `/` and `/teams` | Index the permanent team picker; choose **one** canonical representative after checking current behavior and links. | If `/` remains a useful picker for new visitors and `/teams` is near-identical, canonicalize the duplicate while preserving the saved-team user flow. Do not redirect `/` purely for SEO if it breaks product behavior. |
| `/<team>` | Index all 30 team schedules. | Unique team name, league, season, schedule/status and links in initial crawlable HTML; self-canonical preferred URL. |
| `/<team>/players` | Index all 30 rosters with data. | Accurate current-roster season and explicit previous-season stat labels; empty/unfetched rosters must not look like complete data. |
| `/<team>/players/<id>` | Index active player pages with substantive, accurate profile/stat content and HTTP 200. | Preserve stable IDs and URLs; handle trades/removed players with an explicit retention policy. Do not index a generic “Player not found” shell. |
| `/<team>/games/<id>` | Index useful scheduled game previews and completed box scores only when directly accessible with HTTP 200 and stable content. | Avoid indexing `/games/live` test route or absent IDs. Consolidate duplicate home/away team versions of one game after comparing their genuinely distinct perspective. Prefer a stable canonical representative, while keeping existing team URLs functional. |
| Historical game/player/season pages | **Defer indexing.** | First retain season-specific source data and permanent pages; otherwise return the correct 404/410 for removed IDs. No mass backfill solely for URL count. |
| League landing, standings, statistics | **Opportunity, not current defect.** | Add only if product features exist and provide a distinct useful view. NFL launch needs an NBA/NFL picker and league-aware URLs; preserve current NBA URLs. |

Canonical URLs should be absolute HTTPS `myteam.fans` URLs, self-referential on unique pages, with the same preferred variant in sitemap and links. For a same-game duplicate, choose a representative only after viewing both rendered pages; a home-team URL is a possible low-change convention, not an approved fixed rule. Do not canonicalize unrelated roster and team pages together. [Google canonical guidance](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls).

## 6. Page-template metadata requirements

Generate metadata from the same validated page data used for visible content, preferably in initial HTML. Titles below are patterns, not forced strings; preserve concise readable wording. Do not put a changing live score or countdown in the title if cache/update timing makes it unreliable.

| Template | Title pattern | Description content |
| --- | --- | --- |
| Picker | `NBA Teams, Schedules & Scores | myteam.fans` | Choose any NBA team to see its schedule, scores, roster and player stats; concise brand positioning may follow. |
| Team | `<Team> Schedule & Scores — <season> | myteam.fans` | Team's schedule, next game, scores and verified broadcast information; use correct season. |
| Roster | `<Team> Roster & Player Stats — <season> | myteam.fans` | Current roster plus the **correct labeled season** for available stats. |
| Player | `<Player> Stats & Game Log — <Team> | myteam.fans` | Name, team, available season and actual stat view. Avoid fabricated data for new/empty seasons. |
| Game | `<Away> vs <Home> — <date> Score & Box Score | myteam.fans` | Actual matchup/date and available status; say preview before tip, box score after final. Use unambiguous date/time zone in machine data. |

Each indexable URL: unique `<title>`, useful `<h1>`, optional unique description, canonical, viewport, language, and no accidental `noindex`. Search engines may rewrite title/snippet. Social `og:title`, `og:description`, `og:url`, `og:type=website`, and a stable share image are a separate sharing enhancement, not a ranking promise. Test direct sharing without JS; avoid dynamically generating a new image for every live score. [Google titles](https://developers.google.com/search/docs/appearance/title-link), [descriptions](https://developers.google.com/search/docs/appearance/snippet).

## 7. Structured data requirements

**Initial release:** add only factual `WebSite` with name and canonical home URL, and optionally `BreadcrumbList` where visible navigation matches. `SportsEvent` for individual game pages is a **later opportunity** after those pages return 200 with stable matchup, start time, status, and appropriate venue/location when known. Google's Event guidance focuses on individual event pages, not schedule lists; eligibility is not guaranteed. Do not invent a venue, ticket URL, organizer, or final result. Keep JSON-LD aligned with visible facts and validate representative URLs with Google's Rich Results Test and Bing URL Inspection. No `Article`, review/rating, FAQ, or betting schema. [Google Event guidance](https://developers.google.com/search/docs/appearance/structured-data/event), [structured data policies](https://developers.google.com/search/docs/appearance/structured-data/sd-policies).

## 8. Internal linking and sitemap strategy

Preserve the 30 team anchors, team Games/Players navigation, roster player anchors, and relevant game links. Expose a direct anchor to each indexable game from the schedule where useful, rather than making it available only inside an expanded row; this can be a compact link without changing the row's primary tap target. Do not link to `/games/live` test data in crawlable navigation. A generated XML sitemap should include only canonical, HTTP-200, indexable URLs with meaningful current content, grouped by template if useful. Derive it from authoritative team/player/game data at build time; validate IDs and exclude empty/error pages. `lastmod` reflects substantive content updates, not every scheduled build or clock tick. Add a simple `robots.txt` with a sitemap declaration if none is served; do not disallow pages that need to expose `noindex`. [Google sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap), [crawlable links](https://developers.google.com/search/docs/crawling-indexing/links-crawlable).

## 9. Multi-league SEO architecture

Separate **entity identity** from URL presentation: league, season, team ID/slug, player ID, game ID and source IDs. Maintain one metadata/canonical/sitemap rule per template and a league-aware data contract. Keep today's NBA paths as stable aliases. Before NFL, decide whether new URLs use `/nfl/<team>` and whether NBA stays at its current root paths or gains optional `/nba` aliases; do not silently migrate 30 established team URLs. NFL games have different weekly/season/playoff patterns and data sources. The SEO layer should be driven by validated league data, not basketball-specific string concatenation. Do not create NFL pages before the data and product views work.

## 10. Performance and mobile considerations

No production Core Web Vitals baseline was available. First use GSC field data (if populated), PageSpeed Insights/CrUX and mobile lab runs on picker, team, roster, player and game templates. Track LCP, INP and CLS and compare the same templates before/after. The recommended initial HTML/static generation must **not** ship duplicate large JSON, block live score updates, alter local time display, or remove offline support. Keep a stable crawl snapshot of core facts while the browser enhances fresh/live data. Verify scores have freshness labels and that a cached preview never impersonates a live result. Google describes good 75th-percentile thresholds of LCP ≤2.5 s, INP ≤200 ms and CLS ≤0.1; treat these as targets, not measured current values. [Web Vitals](https://web.dev/articles/vitals/).
